Applied project management case study

Project Lantern

Delivering a resilient campus learning platform under tight time, cost, and connectivity constraints.

Learning purpose. Use this case to practise stakeholder analysis, requirements prioritization, hybrid delivery, governance, risk management, quality, change control, and earned value analysis.

The situation

Northbridge Polytechnic serves 8,000 learners across one urban campus and three satellite centres. Students currently receive course material through email, messaging groups, and shared drives. Files are duplicated, links expire, and instructors cannot tell whether a newer version reached every class. Connectivity at two satellite centres is intermittent, and many learners rely on low-cost mobile devices.

The institution approved Project Lantern: a twelve-week initiative to deliver a secure web platform for publishing course material, tracking acknowledgement, and supporting lightweight quizzes. The approved budget is 24 million naira. The first release must support 2,000 pilot learners and 80 instructors. It must work on narrow screens, tolerate unstable connections without losing submitted work, and provide auditable access control.

Definition of success

  • At least 90% of pilot learners can open assigned material on a mobile device.
  • A submitted quiz answer is never silently lost or duplicated.
  • Only authorized learners can access a course space.
  • Instructors can publish a corrected file and identify its current version.
  • The pilot launches within twelve weeks and does not exceed the approved budget.

1 · Stakeholders and value

Start with people, not features

A stakeholder is any person or group that can affect the project, is affected by it, or believes it may be affected. The team used a power-interest grid to decide how to engage each group. High-power, high-interest stakeholders require close collaboration; high-power, lower-interest stakeholders need concise assurance; high-interest groups with less formal power still need frequent opportunities to shape usability.

StakeholderPrimary needEngagement approach
LearnersFast mobile access and recovery from weak connectionsWeekly usability sessions and pilot feedback
InstructorsSimple publishing and clear version statusWorkflow prototypes and acceptance reviews
RegistryAccurate enrolment and course membershipData mapping and fortnightly decisions
IT operationsObservable, supportable, secure serviceArchitecture reviews and runbook ownership
Executive sponsorVisible educational value within budgetBiweekly exception report

Value hypothesis

The project does not assume that a platform automatically improves learning. Its value hypothesis is narrower: if learners can reliably find the current material, practise with timely feedback, and resume after interruption, then avoidable friction will fall. The pilot must test this hypothesis with observed task completion and interviews rather than vanity measures such as page views alone.

Case tension. The sponsor asks for a public leaderboard to “drive engagement.” Learner representatives warn that it may expose performance, punish late participation, and distract from the core launch. The project manager records the request but does not add it directly to scope.

2 · Requirements and scope

Turn needs into testable boundaries

A requirement is useful when it is specific enough to verify. “The platform should be reliable” is an aspiration. “A retry with the same submission identifier does not create a second quiz attempt” is testable. The team separates functional requirements, which describe behaviour, from non-functional requirements, which describe qualities and constraints.

TypeExampleAcceptance evidence
FunctionalAn instructor publishes one current file per lesson.Version replacement walkthrough
FunctionalA learner resumes an unfinished quiz.Reload and second-device test
Non-functionalControls remain usable at 320 pixels wide.Responsive browser test
Non-functionalEvery data query is scoped to the signed-in user.Cross-user authorization tests

Prioritization

The team uses MoSCoW categories. Must-have items define a viable and safe pilot. Should-have items add significant value but have a workaround. Could-have items are included only if time remains. Won't-have-for-now items are explicit boundaries, not forgotten promises.

  • Must: sign-in, course membership, material publishing, mobile reading, saved quiz attempts, deletion, and audit records.
  • Should: instructor analytics and downloadable class summaries.
  • Could: theme customization and optional profile photographs.
  • Won't for the pilot: public leaderboard, native mobile apps, video hosting, and automated exam grading.

The scope baseline combines the approved requirements, schedule, and budget. A work breakdown structure then decomposes the outcome into manageable deliverables: identity, course spaces, content delivery, quizzes, operations, training, and pilot evaluation. Decomposition improves estimation and ownership; it must not become a list of unrelated technical tasks.

3 · Delivery strategy

A hybrid plan for uncertainty and control

Project Lantern uses a hybrid delivery approach. Fixed governance checkpoints protect budget, privacy, and institutional readiness. Within those boundaries, a cross-functional team works in one-week iterations, demonstrates usable increments, and revises the backlog using evidence from learners and instructors.

Twelve-week outline

WeeksOutcomeDecision
1–2Discovery, baseline, architecture spikeApprove scope and major controls
3–5Identity, course spaces, content flowSecurity and usability review
6–8Quiz flow, persistence, reportingPilot readiness assessment
9–10Hardening, training, data migrationGo/no-go recommendation
11–12Pilot launch, observation, handoverClose, extend, or stop

Why hybrid?

A purely predictive plan would assume that needs and technical risks are already understood. A purely adaptive approach could leave executives without clear cost and readiness gates. Hybrid delivery keeps the outcome, constraints, and decision rights visible while allowing the solution to improve through short feedback cycles.

Definition of done. A feature is done only when its acceptance checks pass, keyboard use is possible, errors are recoverable, privacy controls are reviewed, operational notes are updated, and the product owner accepts the behaviour. Code completion alone is not completion.

Each weekly review asks three questions: What usable value exists now? What evidence changed our assumptions? What is the smallest next step that reduces the greatest uncertainty?

4 · Risk and governance

Make uncertainty discussable

A risk is an uncertain event or condition that may affect objectives. An issue has already happened. The team records each risk with a cause, uncertain event, potential effect, owner, probability, impact, response, trigger, and review date. Multiplying probability by impact creates a useful priority signal, but it does not replace judgment.

RiskPIResponse and trigger
Weak connectivity causes duplicate quiz submissions.45Mitigate with idempotent IDs and retry tests; trigger: duplicate attempt in staging.
Enrolment data arrives late.34Mitigate with an agreed snapshot date; trigger: mapping incomplete at week 4.
Instructors resist a new publishing workflow.33Reduce through co-design and short training; trigger: task success below 80%.

Decision rights

The steering group owns changes to budget, launch date, and pilot population. The product owner orders the backlog inside the approved baseline. The technical lead owns implementation choices that meet the constraints. The security lead can block release when a critical control fails. Clear decision rights prevent both uncontrolled change and decision paralysis.

Escalation by exception

The project manager reports trends and exceptions rather than overwhelming the sponsor with task detail. A variance crosses the escalation threshold when forecast cost exceeds the baseline by 10%, a critical milestone is forecast more than one week late, or a severe privacy or security risk lacks an effective response.

5 · Quality and change

Protect the outcome while learning

Quality assurance improves the process used to create the platform. Quality control inspects the resulting product. Lantern needs both: peer review and automated checks reduce defect introduction, while usability sessions, authorization tests, and acceptance walkthroughs reveal whether the finished behaviour meets the need.

Change-control path

  1. Record the request and the problem it is meant to solve.
  2. Assess value, cost, schedule, risk, privacy, and operational impact.
  3. Identify options, including deferment or a smaller experiment.
  4. Send changes beyond delegated tolerance to the steering group.
  5. Update the baseline, backlog, risks, tests, and communication after approval.

When the sponsor repeats the leaderboard request in week 6, the team offers a safer experiment: private personal progress with no public ranking. The option supports reflection without exposing classmates. Because even this alternative consumes design and testing capacity, it is classified as a Could-have and does not displace launch-critical work.

Quality measures

  • Task completion: learners open an assigned file and submit one quiz without help.
  • Reliability: retries do not duplicate attempts and unsent answers remain visible.
  • Accessibility: labelled controls, visible focus, large-text reflow, and untimed tasks.
  • Security: authenticated, owner-scoped access with tested denial between users.
  • Operability: support staff can identify a failed request without viewing learner answers.
Important distinction. Passing a technical test does not prove that learners understand the material. Product reliability and learning outcomes require different evidence.

6 · Schedule and cost

Use earned value to see the trend

At the end of week 6, the steering group wants to know whether Lantern is merely busy or actually on track. The project uses three earned-value measures:

  • Planned value (PV): budgeted cost of work scheduled.
  • Earned value (EV): budgeted cost of work actually completed.
  • Actual cost (AC): cost incurred for completed and incomplete work.

The total budget, or budget at completion (BAC), is ₦24,000,000. By week 6, the baseline planned 50% completion, so PV is ₦12,000,000. Accepted deliverables represent 40% of the total budget, so EV is ₦9,600,000. Actual spending is ₦10,800,000.

Schedule performance index: SPI = EV / PV = 9.6 / 12.0 = 0.80
Cost performance index: CPI = EV / AC = 9.6 / 10.8 = 0.89
Simple estimate at completion: EAC = BAC / CPI = 24.0 / 0.89 ≈ ₦26.97 million

An SPI below 1 indicates that less work has been earned than planned. A CPI below 1 indicates that the project is receiving less budgeted value than each naira spent. If current cost efficiency continues, the simple EAC forecasts an overrun of about ₦2.97 million. The indices are signals, not explanations: the team must investigate causes before selecting a response.

Management response

Analysis shows that enrolment integration and accessibility rework caused most variance. The team protects the security and accessibility acceptance criteria, defers optional analytics, assigns a specialist to the data mapping, and reforecasts the remaining work. It does not hide the variance by declaring partially tested features complete.

7 · Decision point and lessons

Recommend a controlled pilot

By week 10, critical authorization tests pass, mobile task completion reaches 92% in the rehearsal group, and no duplicate submissions occur during network interruption tests. Instructor publishing is usable but slower than expected. The forecast remains above the original budget, although deferring optional analytics reduces the estimate to ₦25.4 million.

The project manager recommends a controlled pilot rather than an institution-wide launch. The pilot is limited to 2,000 learners, includes daily operational review for the first week, and defines rollback conditions. Approval requires an explicit budget exception and acceptance of the remaining instructor-workflow risk.

Lessons from Project Lantern

  1. Start with the learner problem and define measurable success before choosing features.
  2. Translate broad expectations into acceptance evidence and explicit exclusions.
  3. Use short feedback cycles inside clear governance and decision rights.
  4. Treat risk, privacy, accessibility, and operations as design inputs from the start.
  5. Separate progress signals from explanations; investigate variance before acting.
  6. A controlled pilot can be a responsible success when uncertainty remains.
